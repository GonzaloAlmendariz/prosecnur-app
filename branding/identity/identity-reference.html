Reglas de uso

  • Proporción 60/30/10: superficies frías dominan, el navy estructura, el acento (modular o señal) aparece de forma puntual e intencional
  • El acento es chrome, el semántico es significado: éxito/alerta/peligro/info jamás se sustituyen por el color del módulo
  • Acento inyectado por variable (--module-accent / --home-mod-accent / reasignación de --pulso-primary); nunca hex de módulo hardcodeado por regla
  • Cada acento modular tiene variantes soft (alpha 0.12-0.13) y border (alpha 0.30-0.32) definidas en theme.css; ver extensions.interaction_alphas para los valores exactos de interacción del navy (soft 8%, border 18%, focus 15%, ring 12%)
  • Los semánticos operan en triadas bg/border/fg sobre superficie clara; el token base (success/warn/danger) es el acento del estado; info usa el navy translúcido (bg rgba(0,36,87,0.04), border = primary-border, fg = primary)
  • El peligro de chart (#DC2626) y el carmesí UI (#BE123C) son tokens distintos a propósito: no unificarlos
  • El marcador repeat (naranja suave) es semántico transversal —pertenencia a estructura repetida roster—, no un acento de módulo; se superpone a cualquier paleta sin competir
  • Dos tintas máximo en la marca (navy + blanco); el color vivo pertenece al sistema, nunca al logo
  • Colores solo con tokens --pulso-* dentro de la app y --prosecnur-* fuera de ella; si un color no está en la paleta de visualización, no entra a un gráfico
  • Las triadas semánticas deben sostener contraste AA de texto sobre su fondo; la verificación formal vive en el check de accesibilidad

  • Toda vista es enlazable: ruta = módulo, query = el resto (/monitoreo?modo=territorial&seccion=avance&pestana=ump&panel=filtros). Params canónicos modo/seccion/pestana/panel/foco; los nombres viejos (family, tab, stage, mesa, desk, step, reporte) se leen como alias pero nunca se escriben
  • Un overlay nuevo se conecta con usePanelDireccionable, no con un useState suelto; el sidebar de objetos expande empujando el canvas por grid, nunca como overlay flotante
  • Módulos canónicos y sus rutas: Bitácora (/bitacora), Cálculo de muestra (/calc-muestra), Editor de formularios (/editor-xlsform), Hojas de ruta (/hojas-ruta), Fichas QR (/recopiladores), Monitoreo (/monitoreo), Procesamiento (/procesamiento), Dashboard (/tablero)

Economía del chrome

  • Sin franjas de título: los módulos no llevan H1 visible (headerMode="sr-only"); sin títulos interiores redundantes en paneles
  • Datos en el primer viewport: exploradores, filtros y resúmenes son herramientas subordinadas
  • Jerarquía de contenedores: Shell → PageFrame con layouts document (lectura/formularios con scroll de página), workbench (rail + área principal con scroll interno), canvas (superficie visual con área mínima preservada), data (tabla/grilla con scroll interno)
  • Dueños de scroll: page (el área principal scrollea) · body (el body del PageFrame scrollea) · panels (paneles internos, degradando a .pulso-main en compact/short)
  • Un solo dueño de scroll por pantalla (No Scroll Jail); overflow:hidden solo oculta contenido decorativo o delega a un descendiente scrollable

Responsive

  • Breakpoints canónicos: desktop (>1320px y >720px de alto) · compact desktop (≤1320px o ≤720px de alto: reduce padding, compacta encabezados, toolbars envuelven) · narrow desktop (≤900px: workbenches apilan rail y contenido) · short desktop (≤700px de alto: apilan aunque el ancho alcance)
  • Matriz base de QA: 1710x1107 · 1440x1000 · 1366x768 · 1280x720 · 1024x600
  • Presets manuales (pulso.layoutPreset en localStorage, nunca en el .pulso): auto/large/portable/portable-compact/compact/short; el shell expone data-pulso-layout-preset/density/mode
  • Ninguna ruta deja contenido vertical inaccesible por cadenas de height:100% + overflow:hidden; si una pantalla crece al compactarse debe existir un dueño de scroll visible y alcanzable
  • El shell no introduce scroll horizontal global; el fallback de scroll vive en .pulso-main, no en body
